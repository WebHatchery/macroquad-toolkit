# Artwork and Sprite Inventory

Last audited: 2026-08-12

## Scope and current status

This repository is a reusable rendering and game-systems library, not a game
with a fixed cast, setting, or art direction. It therefore has no game-specific
cast or world to illustrate. It now includes a deliberately neutral reference
pack for toolkit documentation and smoke tests; consuming games still own their
actual portraits, world sprites, title art, and content icons.

The toolkit currently has no runtime dependency on external bitmap artwork.
Its buttons, panels, cards, plaques, tabs, scrollbars, badges, form controls,
notification toasts, debug overlay, particles, fades, floating text, and CRT
overlay are drawn procedurally by Rust code. The only bundled visual asset is
the UI font.

| Asset | Location | Status | Notes |
| --- | --- | --- | --- |
| Rajdhani SemiBold font | `assets/fonts/Rajdhani-SemiBold.ttf` | Complete | Embedded by `ui::font`. |
| Rajdhani license | `assets/fonts/OFL-Rajdhani.txt` | Complete | Keep beside the font. |
| Character portraits | `assets/images/portraits/portrait_archivist_neutral.png` | Complete | Neutral reference portrait for documentation/gallery scenes. |
| Gameplay sprites or atlases | `assets/images/sprites/drone_atlas.png` | Complete | Exact 4x2, 128px-cell atlas; nearest-filtered. |
| Billboard sprite | `assets/images/sprites/drone_billboard.png` | Complete | Transparent upright frame for 3D billboard examples. |
| UI icon atlas + glyphs | `assets/images/ui/icons/semantic_icons.png` + 50 individual PNGs | Complete | 4x4 reference sheet plus named 48px glyphs. |
| Missing-texture fallback | `assets/images/missing_texture.png` | Complete | 64x64 RGBA, color-blind-readable crosshatch. |
| Panel/chrome textures | None | Procedural by design | Current surfaces remain code-drawn. |
| CRT masks/vignette | Generated at runtime | Complete | Built by `fx::crt`; no source art is needed. |
| Catalog thumbnail | None | Not applicable | This is a library, not a catalog game. |

**Current blocking art TODO: none.** The required reference pack is implemented
and loaded through `artwork::load_toolkit_artwork` / `load_toolkit_icons`. Do not add decorative bitmap assets merely
to duplicate visuals already generated by the toolkit. Add an asset only when a
public component or example consumes it and the asset improves clarity,
accessibility, or demonstrates a supported rendering path.

### Semantic icon set (complete)

The toolkit now ships one coherent 50-glyph family and a 4x4 visual reference
sheet. Consumers may load either the individual named files or the sheet.

| Family | Icons to cover | Required states |
| --- | --- | --- |
| Window/navigation | close, back, forward, home, menu, expand, collapse | normal, disabled |
| Playback/session | play, pause, resume, stop, restart | normal, disabled |
| Persistence | save, load, autosave/sync, delete | normal, disabled; destructive variant for delete |
| Settings/audio | settings, music, sound, mute, fullscreen | normal, disabled; on/off where applicable |
| Information | help, info, success, warning, danger/error | semantic color must not be the only distinction |
| Lists/data | search, filter, sort ascending, sort descending, add, remove, edit | normal, disabled |
| Game screens | inventory, equipment, map, objectives/quests, journal/log, achievements | normal, selected, disabled |
| Status | lock, unlock, visible, hidden, favorite, notification | normal, active/selected where applicable |
| Touch hints | tap, drag, swipe, pinch | diagrammatic gesture plus short text in the consuming UI |

Icon delivery requirements:

- [ ] Author icons on a consistent 24 x 24 design grid with a 2 px safe area.
- [ ] Export individual 48 x 48 RGBA PNG masters for sharp 2x display.
- [ ] Use transparent backgrounds and consistent apparent stroke weight.
- [ ] Keep silhouettes recognizable at a 20-24 px rendered size.
- [ ] Never encode success, warning, or danger by color alone.
- [ ] Provide state changes through the widget tint/opacity API where possible;
  avoid separate hover and pressed files unless the silhouette changes.
- [ ] Keep labels available for unfamiliar actions. An icon must not become the
  only visible path to a required action unless its meaning is unambiguous.
- [ ] Give every icon control at least the toolkit's 44 x 44 logical-pixel touch
  target even when the drawn icon is smaller.

## Consuming-game portrait checklist

Portraits are game-owned. For every game using this toolkit, build a portrait
manifest from its actual character/content data; do not infer a cast from this
library. Include one row for every speaking, selectable, recruitable, hostile,
or otherwise portrait-bearing identity.

Use this table in the game repository:

| ID | Character/role | Usage | Expressions/variants | Crop | Status |
| --- | --- | --- | --- | --- | --- |
| `portrait_<id>_neutral` | `<name>` | dialogue/profile/etc. | neutral | bust/head | [ ] |
| `portrait_<id>_<variant>` | `<name>` | `<trigger>` | speaking/hurt/angry/etc. | same as neutral | [ ] |
| `portrait_unknown` | Unknown/hidden identity | fallback/locked content | obscured silhouette | same frame | [ ] |

Portrait requirements:

- [ ] Use a consistent camera angle, scale, lighting direction, outline/render
  style, and eye line across the cast.
- [ ] Keep head, face, hair, hats, ears, and other identifying features inside
  the safe area for every supported crop.
- [ ] Export a 1024 x 1024 layered/source master and a 512 x 512 RGBA delivery
  PNG unless the consuming layout documents another size.
- [ ] Preserve transparent backgrounds when portraits overlay dialogue or UI.
  Use JPEG only for intentionally opaque, rectangular illustrations.
- [ ] Keep each expression aligned to the neutral portrait so swapping frames
  does not make the character jump.
- [ ] Include alternate outfit, injury, age, disguise, faction, or progression
  variants only when game state can actually display them.
- [ ] Include a deliberate unknown/locked/dead fallback only when the game has
  that state; do not use a missing portrait as a design state.
- [ ] Verify readability at the smallest in-game display size and on both light
  and dark surfaces.
- [ ] Document asset provenance and confirm commercial-use rights.

## Consuming-game sprite checklist

The toolkit supports standalone `Sprite` textures, uniformly gridded
`SpriteAtlas` sheets, deterministic recolors, and upright 3D billboards. A game
should inventory every rendered entity and state before art production.

### Entity and world inventory template

| ID | Subject | View | Frame size | Clips/frames | Variants | Status |
| --- | --- | --- | --- | --- | --- | --- |
| `sprite_<id>` | `<entity>` | side/top/isometric/front | `<w>x<h>` | idle, move, action, hit, defeat | tint/outfit/faction | [ ] |
| `tile_<id>` | `<terrain/prop>` | top/isometric | `<w>x<h>` | static or animated | edge/damage/season | [ ] |
| `billboard_<id>` | `<3D subject>` | front-facing upright | `<w>x<h>` | static or atlas-driven | tint/faction | [ ] |
| `fx_<id>` | `<effect>` | screen/world | `<w>x<h>` | start, loop, finish | color/intensity | [ ] |

For each game, explicitly check for:

- [ ] Player characters and all equipment/appearance states shown in-world.
- [ ] NPCs, enemies, bosses, summons, companions, and neutral creatures.
- [ ] Terrain tiles, transitions, edges, corners, obstacles, doors, and damaged
  or destroyed states.
- [ ] Pickups, resources, projectiles, weapons, tools, vehicles, and interactable
  props.
- [ ] Spawn, idle, movement, primary action, secondary action, hit, defeat, and
  recovery frames where gameplay exposes those states.
- [ ] Shadows, selection rings, targeting markers, path/destination markers,
  and fog/visibility markers when not drawn procedurally.
- [ ] Environmental and combat effects not covered by procedural particles,
  floating text, fades, travel paths, or screen shake.

Sprite delivery requirements:

- [ ] Export RGBA PNG for transparency. Retain source files outside the runtime
  asset directory or in a clearly named source-art directory.
- [ ] Use nearest filtering for pixel art and linear filtering for painted or
  high-resolution art; declare exceptions in the texture manifest.
- [ ] Use identical cell width and height throughout a `SpriteAtlas`. The
  toolkit computes columns from texture width and does not consume packed-atlas
  metadata.
- [ ] Place every atlas frame on its cell's exact pixel boundary with no hidden
  padding differences. Keep feet/contact points and pivots visually stable.
- [ ] Reserve transparent gutter pixels if linear filtering could sample an
  adjacent frame. Otherwise prefer standalone textures.
- [ ] Do not rotate frames inside an atlas. Runtime horizontal flipping is
  supported; vertical flipping is not exposed by `SpriteAtlas::draw_frame`.
- [ ] Keep recolor target regions distinct in HSV from protected details. Test
  several seeds for accidental recoloring of skin, outlines, highlights, and
  transparency.
- [ ] For billboard sprites, keep the subject upright, centered horizontally,
  and grounded at the bottom-center. Leave transparent clearance for effects
  and tall features.

## Consuming-game UI artwork checklist

The toolkit's default UI needs no bitmap chrome. A game should add UI art only
where its design calls for more than the procedural surfaces.

- [ ] Game logo/title treatment, including a compact version if the pause or
  loading UI uses one.
- [ ] Title/menu background or key art, with safe zones for controls and text.
- [ ] Screen-specific backgrounds, frames, dividers, corner ornaments, and
  nine-slice panels only when procedural surfaces cannot achieve the art
  direction.
- [ ] Button icons and tab/navigation icons actually referenced by visible
  controls.
- [ ] Resource, currency, health, armor, energy, ammo, status-effect, rarity,
  and faction icons actually surfaced by game data.
- [ ] Inventory item, equipment, ability, spell, recipe, building, unit, quest,
  and achievement icons for every authored definition that displays an image.
- [ ] Locked, unknown, empty-slot, unavailable, cooldown, selected, and newly
  acquired states where tinting or procedural overlays are insufficient.
- [ ] Cursor, targeting reticle, drag handle, map pins, selection marks, and
  touch-gesture illustrations where the game uses them.
- [ ] Tutorial diagrams that name or point to the exact visible tap target or
  gesture; never rely on a keyboard-only illustration.
- [ ] Loading artwork and platform/store artwork only when the target platform
  or publishing process requires them.
- [ ] A root-level `catalog_thumbnail.png` for each catalog **game**. Prefer a
  title-screen capture. Do not add one to this toolkit library.

For icons sourced from game data, the content definition and art inventory must
match one-for-one. Add a validation test in the consuming game that reports
missing or duplicate keys rather than relying on visual QA to find gaps.

## File organization and naming

Recommended layout for a consuming game:

```text
assets/
  images/
    backgrounds/
    portraits/
    sprites/
    tiles/
    ui/
      icons/
      frames/
      tutorials/
  textures.json
source_art/                 # layered/editable masters; not loaded at runtime
```

Use lowercase `snake_case` names with the semantic identity first and the state
last, for example `guard_idle.png`, `guard_hurt.png`,
`portrait_guard_angry.png`, and `icon_sound_muted.png`. Do not encode a final
screen position or arbitrary revision number in a runtime filename.

A texture manifest entry should make filtering explicit:

```json
{
  "textures": [
    {
      "key": "portrait_guard_neutral",
      "path": "assets/images/portraits/portrait_guard_neutral.png",
      "filter": "linear"
    },
    {
      "key": "guard_atlas",
      "path": "assets/images/sprites/guard_atlas.png",
      "filter": "nearest"
    }
  ]
}
```

PNG is the default for sprites, portraits with transparency, UI chrome, and
icons. JPEG is supported by the toolkit and is appropriate for opaque painted
backgrounds or key art where its artifacts are acceptable. Avoid JPEG for
alpha-dependent art and crisp pixel art. SVG is not a runtime texture format;
retain it as a source master and export PNG deliveries.

## Definition of done for any new visual asset

- [ ] A real screen, component, data definition, or documented example consumes
  the asset; it is not speculative decoration.
- [ ] Runtime filename, texture key, dimensions, crop/pivot, filter mode, and all
  required states are documented.
- [ ] Alpha edges are clean over light, dark, and saturated backgrounds.
- [ ] The asset remains legible at minimum size and is not clipped at common
  desktop-browser sizes.
- [ ] Every required interaction remains possible through a visible 44 x 44
  logical-pixel tap/click target; keyboard shortcuts are supplemental.
- [ ] Semantic state is understandable without color alone.
- [ ] The asset loads through `macroquad_toolkit::assets::AssetManager` or an
  `AssetPack`, with an obvious fallback for missing files.
- [ ] Native and WASM paths use identical case and separators in the manifest.
- [ ] Source, author, license, and allowed uses are recorded.
- [ ] The consuming game's `publish.ps1` passes.
- [ ] Relevant screens are captured in `docs/verification/`, replacing an older
  capture of the same state instead of creating a duplicate.

## Audit triggers

Re-audit this document whenever the toolkit adds an icon-bearing widget,
portrait component, non-uniform atlas support, nine-slice rendering, tilemap
renderer, themed bitmap skin, or new public example. A consuming game must keep
its own concrete art inventory; this library-level document is the contract and
checklist, not a substitute for a game's character and content manifest.
